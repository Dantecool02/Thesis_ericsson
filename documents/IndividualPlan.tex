\section{Background \& Objective}

Retrieval-Augmented Generation (RAG) has become a standard way to ground large language models in private or changing data \cite{gao2023ragsurvey}. However, vector-only retrieval often struggles when the answer depends on linking facts across documents or comparing distributed attributes. Recent graph-based systems such as GraphRAG and LightRAG show that structured retrieval can make such questions more tractable by explicitly modeling entities, relations, and higher-level document structure \cite{edge2024graphrag,lightrag2024}. At the same time, adaptive retrieval work such as Self-RAG and Adaptive-RAG argues that not every query should trigger the same retrieval behavior, since indiscriminate retrieval or always using the most sophisticated strategy can introduce unnecessary computational overhead \cite{asai2023selfrag,jeong2024adaptiverag}. This creates a broader scientific and practical problem: expensive retrieval should ideally be used only when it is actually needed.

Ericsson works with large internal technical repositories where information is fragmented across documents and cannot be assumed to exist in public model pretraining. In such settings, graph-enhanced retrieval can improve answer quality, but using it for every query is inefficient. The company interest is therefore to support high-quality question answering while avoiding unnecessary token and inference cost.

An important knowledge gap remains between these two research directions. Existing graph-based RAG work motivates richer retrieval, and adaptive retrieval work motivates selective computation, but it is still unclear whether the specific choice between cheap vector retrieval and more expensive graph-enhanced retrieval can itself be delegated to a lightweight task-specific classifier. If the routing decision requires a large general-purpose model, then some of the expected efficiency gain is lost already at the control layer. This makes retrieval-mode selection an interesting research problem rather than only an implementation detail \cite{hu2024routerbench,benayas2024encoder}.

The objective of the project is therefore to design and evaluate a learned routing layer that decides whether cheap vector retrieval is sufficient or whether more expensive graph-enhanced retrieval is required. The desired outcome is not only a working routing policy, but also empirical evidence about whether retrieval-mode selection can be learned as a narrow text classification problem, and whether such a model can reduce unnecessary token cost while preserving access to graph-enhanced retrieval for queries that truly require it.

The project requires knowledge of machine learning, transformer-based text classification, retrieval-augmented generation, and experimental evaluation. Prior familiarity with Python, PyTorch, Hugging Face, and applied GenAI systems is especially relevant for implementing the router and the surrounding evaluation pipeline.

\section{Research Question \& Method}

\subsection{Question} Within a fixed Hybrid RAG setting, how predictable is the distinction between queries for which vector retrieval is sufficient and queries for which graph-enhanced retrieval is required, based on the query text alone?

\subsection{Objectives}
\begin{itemize}[label=--]
    \item Implement a reproducible pipeline for executing LightRAG in both \emph{Naive} and \emph{Mix} modes and logging answer outputs and cost-related metadata.
    \item Construct a supervised routing dataset by labeling queries with the minimum viable retrieval mode.
    \item Fine-tune an encoder-only classifier to predict whether graph-enhanced retrieval is required from the query text alone.
    \item Evaluate the resulting router first as a held-out label-prediction model and second as a routing policy through offline simulation.
\end{itemize}

\emph{Tasks and challenges.}
\begin{itemize}[label=--]
    \item \emph{Task 1: Corpus preparation and indexing.} Build and maintain a reproducible 2WikiMultihopQA indexing pipeline in LightRAG. The main challenge is incremental indexing and the heavy compute necessary for graph creation.
    \item \emph{Task 2: Routing label generation.} Execute both retrieval modes and use LLM-as-a-Judge to decide whether vector retrieval was sufficient or whether graph-enhanced retrieval was required. Queries where both modes fail or the judgment is unclear will be excluded from router training. The main challenges are judge reliability, label noise, and class balance \cite{zheng2023judge}.
    \item \emph{Task 3: Router training.} Fine-tune a lightweight encoder such as ModernBERT-base \cite{warner2024modernbert} and compare it to a simpler baseline such as TF-IDF with logistic regression. The main challenge is to learn a meaningful decision boundary.
    \item \emph{Task 4: Evaluation.} Evaluate the router first on held-out routing labels and then through thresholded offline simulation. The main challenge is to keep the primary evaluation focused on whether the router learns the judged routing pattern, while still showing the practical implications of the learned decision boundary. In the offline simulation, each threshold must map cleanly to both held-out label performance and cumulative token cost so that the resulting operating points can be compared.
\end{itemize}

\subsection{Method} The primary benchmark will be 2WikiMultihopQA, which provides gold questions, answers, and supporting evidence \cite{ho2020twowiki}. Each query will be executed in LightRAG's \emph{Naive} and \emph{Mix} modes. An LLM Judge will compare both outputs against the benchmark answer and support facts, decide whether vector retrieval was already sufficient or whether graph-enhanced retrieval was required, and mark unclear or unsuccessful cases for exclusion from router training. This uses LLM-as-a-Judge as a scalable but imperfect labeling mechanism, rather than as an unquestioned source of truth \cite{zheng2023judge}. The resulting dataset will be split into train, validation, and test subsets after a pilot phase, with attention to both 2Wiki question types and the observed routing-label distribution. A lightweight encoder-only router will then be fine-tuned and compared to static baselines and a simple classical baseline. The primary evaluation will measure how well the router predicts held-out routing labels. A secondary evaluation will use held-out offline simulation together with the precomputed token usage of both retrieval modes to analyze how different thresholds trade label-prediction performance against token cost. This method is appropriate because it lets the thesis isolate the routing problem while keeping the retrieval environment fixed \cite{hu2024routerbench,jeong2024adaptiverag,benayas2024encoder}.

\subsection{Ethics} The main benchmark is public and therefore does not raise major privacy concerns in the core experimental setup. If an Ericsson extension is added later, confidentiality, access control, and careful handling of internal technical material become essential. A second ethical consideration is methodological: because the routing labels are assigned with LLM-as-a-Judge, the work must acknowledge the risk of noisy or biased labels and treat unclear cases conservatively rather than forcing them into the training data \cite{zheng2023judge}. This project therefore aims to use the judge as a controlled labeling mechanism rather than as an authority on open-ended answer quality.

\subsection{Sustainability} The project is directly motivated by computational sustainability. If graph-enhanced retrieval is applied to every query, token usage and inference cost increase unnecessarily for queries that could have been handled by vector retrieval alone. A successful router would therefore reduce redundant retrieval and generation cost while preserving access to the stronger retrieval mode when it is actually needed. In that sense, the thesis investigates whether adaptive routing can make Hybrid RAG systems more resource-efficient without turning the routing step itself into another expensive model call.

\subsection{Limitations} The router uses the query text only. The thesis evaluates the routing decision within LightRAG, where the abstract distinction is operationalized as \emph{Naive} versus \emph{Mix}. The primary benchmark is 2WikiMultihopQA, Ericsson data is treated as an optional extension rather than a core dependency.

\subsection{Risks} The main risks are noisy judge labels, an imbalanced final label distribution, and practical limits on API cost or throughput. These risks will be handled through a pilot phase, incremental data generation, exclusion of unclear cases from router training, and keeping Ericsson data optional rather than central to the scientific contribution.

\section{Evaluation \& News Value}

\subsection{Evaluation} The research question will be considered adequately answered if the project shows, on held-out data, that the distinction between vector-sufficient and graph-required queries is predictable from the query text with consistent reliability. The primary evaluation will therefore focus on held-out label-prediction metrics such as precision, recall, and F1, which directly measure whether the learned router captures the judged routing distinction. As a secondary evaluation, the router's predicted probabilities will be turned into thresholded routing policies, and each threshold will be analyzed in terms of the total and average token cost it would imply compared with static baselines such as always \emph{Naive} and always \emph{Mix}.

\subsection{Expected scientific results} The expected scientific contribution is empirical evidence about how predictable the distinction between vector-sufficient and graph-required queries is from query text alone in a fixed Hybrid RAG setting. In relation to prior work on adaptive retrieval, model routing, and efficient text classification \cite{jeong2024adaptiverag,hu2024routerbench,benayas2024encoder}, the thesis contributes a more narrowly defined study of retrieval-mode selection as a supervised prediction problem. The expected result is therefore not merely a working router, but a clearer account of whether this routing distinction can be learned with useful reliability by a lightweight task-specific classifier, and how that predictability relates to the token-cost savings targeted by adaptive retrieval.

\subsection{Innovation and news value} Prior work such as Self-RAG and Adaptive-RAG has shown the value of adaptive retrieval, while RouterBench has framed routing more broadly as an important systems problem \cite{asai2023selfrag,jeong2024adaptiverag,hu2024routerbench}. However, these works do not specifically study retrieval-mode selection inside a fixed Hybrid RAG system as a narrow supervised prediction task between vector retrieval and graph-enhanced retrieval. The novelty of this thesis is therefore to position that choice, operationalized through LightRAG's \emph{Naive} and \emph{Mix} modes, as a specialized routing problem that may be solvable by a lightweight fine-tuned classifier rather than by a larger proprietary or decoder-based controller \cite{lightrag2024,benayas2024encoder,warner2024modernbert}. The broader relevance is that this could reduce unnecessary compute in adaptive RAG systems while preserving access to graph-enhanced retrieval for the subset of queries that truly require it.

\section{Pre-Study}

The pre-study focuses on hybrid and graph-based retrieval, multi-hop benchmark choice, adaptive retrieval and routing, encoder-only text classifiers, and LLM-as-a-Judge as a labeling mechanism. These topics are covered in the separate pre-study document, which functions as the literature-study basis for the degree project. The state of the art will therefore be built from both a literature review and a small exploratory engineering pilot on 2WikiMultihopQA. Preliminarily important references include LightRAG \cite{lightrag2024}, 2WikiMultihopQA \cite{ho2020twowiki}, RouterBench \cite{hu2024routerbench}, Adaptive-RAG \cite{jeong2024adaptiverag}, and ModernBERT \cite{warner2024modernbert}.
